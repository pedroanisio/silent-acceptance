# silent-acceptance

Home of the **Silent Acceptance** specification (formerly *PALS's LAW*) and its two
companion tools: `pals-check`, a small Python CLI that audits the specification's
Markdown source for reference integrity, math consistency, and formal schema
structure, and `silent-acceptance-lint`, a TypeScript linter that checks *code* for
the defect the specification names. The repository was renamed from `pals-check` with
v2.0.0; GitHub redirects the old URL, and the audit tool keeps the old name.

The audit takes the source document in [`SILENT_ACCEPTANCE-v2.1.0.md`](./SILENT_ACCEPTANCE-v2.1.0.md),
runs a deterministic analysis pipeline, and writes machine-readable artifacts to
[`output/`](./output). The v1.x sources (`PALS_LAW-v1.5.*.md`) stay in the repository
and remain auditable, because the Zenodo records for those versions carry reports
generated by this tool.

## What the audit does

- Extracts and normalizes the references declared in the spec (§4, §4.1, §4.2).
- Optionally fetches DOI and arXiv targets to compare claimed vs fetched metadata.
- Parses display-math blocks and runs consistency checks over the formal claims.
- Builds a formal schema for symbols, claims, error classes, and practitioner artifacts.
- Signs generated JSON artifacts and emits a binding certificate for tamper-evident verification.
- Emits JSON artifacts that can be reviewed, diffed, or consumed by downstream tooling.

For the current checked-in spec, the generated report summarizes:

- `15` references
- `7` math blocks
- `11` passed checks
- `0` failed checks

### Two layouts, one checker

The spec was restructured in v2.0.0 (asymmetry moved to §7, corollaries to §9,
artifacts to §10). Every section identifier the checker relies on lives in a
`SpecLayout` in [`pals_check/constants.py`](./pals_check/constants.py); the layout
is chosen from the document's major version, so `python -m pals_check PALS_LAW-v1.5.4.md`
and `python -m pals_check SILENT_ACCEPTANCE-v2.1.0.md` both audit cleanly. The
v2.1.0 vocabulary (acceptability predicate, $\tau$, conditional-hazard pipeline form)
is gated on the document's exact version. The contract tests in
`tests/test_drift_guards.py` run against all three published specs (v1.5.4, v2.0.0,
v2.1.0).

The test suite never writes into the repository's `output/`; an integration test
asserts the committed artifacts are byte-identical before and after the CLI run.

## Quickstart

### Requirements

- Python `3.10+`
- Node `24` for the linter (no runtime dependencies; TypeScript is run directly)
- `pandoc` and `lualatex` for `make pdf` (optional)

### Run the spec audit from source

```bash
python3 -m pals_check SILENT_ACCEPTANCE-v2.1.0.md --no-verify
```

This writes:

- [`output/pals_law_report.json`](./output/pals_law_report.json)
- [`output/pals_law_schema.json`](./output/pals_law_schema.json)
- [`output/pals_law_certificate.json`](./output/pals_law_certificate.json)

The output file names keep their original `pals_law_` prefix so that downstream
consumers and the Zenodo records stay stable across the rename.

If you want live reference verification against DOI and arXiv URLs, omit `--no-verify`:

```bash
python3 -m pals_check SILENT_ACCEPTANCE-v2.1.0.md
```

### Run the code linter

```bash
node silent-acceptance-lint/src/cli.ts path/to/your/src
```

It reports every LLM call site (Anthropic, OpenAI, Google, Vercel AI SDK, Bedrock,
Ollama by default; configurable) that has no verification boundary declaration in
scope, every declaration in which no error class is `COVERED` (S = ∅, which no
mitigation note excuses), every declaration with no `ACCEPTANCE_AUTHORITY`, and every
declaration with no `SOLVER_CONFIGURATION_ID` pin; the v2.0.0 `MODEL_VERSION` field
is accepted with a deprecation warning. Exit code 1 on findings.

## CLI usage

```text
python -m pals_check <path_to_md_file> [--no-verify] [--package]
python -m pals_check --check-sig <json_file>
python -m pals_check --verify-cert <cert.json> <spec.md> [report.json] [schema.json]

--no-verify    Skip network fetching of reference URLs
--package      Bundle spec + outputs into a signed .zip archive
--check-sig    Verify the digital signature of an output file
--verify-cert  Verify a certificate against source artifacts
```

The project also exposes a `pals-check` console script in [`pyproject.toml`](./pyproject.toml)
for environments where the package is installed.

The CLI prints a terminal summary with:

- document version, layout, and content hash
- normalized references and verification status
- math consistency checks
- schema totals for symbols, claims, error classes, and artifacts
- error-class coverage warnings
- per-artifact signature metadata
- certificate digests binding spec, report, and schema together

## Generated artifacts

### `pals_law_report.json`

Operational audit output containing normalized references, extracted math blocks,
check results, schema summary, warnings, aggregate counters, and `_signature`
metadata proving the payload digest and signing tool version.

### `pals_law_schema.json`

Formal schema output containing symbols and type signatures, formal claims and
epistemic status (including the v2 `prescription` status for the Verification
Boundary Principle), error class definitions, practitioner artifacts, the dependency
graph, the structural vs semantic error-class partition, the layout name, and
`_signature` metadata.

### `pals_law_certificate.json`

Standalone binding certificate containing SHA-256 digests for the source spec,
report payload, and schema payload; generation timestamp and tool version;
aggregate check counts at generation time; and a certificate binding digest used
to verify the certificate itself.

You can verify outputs after generation with:

```bash
python3 -m pals_check --check-sig output/pals_law_report.json
python3 -m pals_check --check-sig output/pals_law_schema.json
python3 -m pals_check --verify-cert \
  output/pals_law_certificate.json \
  SILENT_ACCEPTANCE-v2.1.0.md \
  output/pals_law_report.json \
  output/pals_law_schema.json
```

## Publishing a new version to Zenodo

`zenodo-sdk/examples/publish-v2.ts` creates the next version under the existing
concept DOI. It is a dry run by default; `--draft` creates and uploads the draft for
inspection on Zenodo; `--publish` mints the DOI, which is irreversible for files.
Run `make regen` and `make pdf` first so the uploaded artifacts match the source.

## How the pipeline is organized

The core modules under [`pals_check/`](./pals_check) are intentionally small and direct:

- [`pals_check/constants.py`](./pals_check/constants.py) holds the error-class enum, claim statuses, and the two `SpecLayout` definitions.
- [`pals_check/references.py`](./pals_check/references.py) collects references and optionally verifies them over the network.
- [`pals_check/math_checker.py`](./pals_check/math_checker.py) extracts `$$...$$` blocks and checks formal consistency.
- [`pals_check/schema.py`](./pals_check/schema.py) builds the structured schema representation.
- [`pals_check/report.py`](./pals_check/report.py) assembles the final audit report.
- [`pals_check/signing.py`](./pals_check/signing.py) signs artifacts and verifies report/schema certificates.
- [`pals_check/__main__.py`](./pals_check/__main__.py) provides the CLI entry point.

## Scope and limitations

- The tool is tailored to the two published structures of the spec, including section-aware parsing and hardcoded semantic mappings; a further restructure means a new `SpecLayout`.
- Reference verification depends on live network access and publisher behavior; DOI hosts may block automated requests.
- Signatures and certificates make output tampering evident, but they do not replace independent validation of the spec's claims or references.
- The linter is a presence check on the boundary declaration, not a dataflow analysis; it cannot judge whether a declared verifier is adequate.
- The generated JSON is only as current as the last regeneration step. `make check` is the intended guard against output drift.

If you are editing the specification itself, the normal workflow is: update the Markdown source, run `make check`, review the JSON diff, and commit the regenerated artifacts together.
